Your agent is about to sign. Should it?

Truvian Shield is an execution-safety checkpoint for on-chain agents. Before a transaction is signed, Shield asks live Telegraph Protocol miners four questions — about fees, the counterparty, the dollar value and the protocol's liquidity — and returns a deterministic SAFE / CAUTION / BLOCK verdict with per-check evidence, cost, latency and a node-issued signal hash anyone can verify.

The problem

Agents sign blind.

An autonomous agent that moves money on-chain makes its decision on whatever one RPC or one API told it a moment ago. Nobody vouched for that data, nobody paid for it, and there is no record of where it came from.

  • A fee spike looks like a normal fee. The agent signs into congestion and overpays, or the transaction stalls.
  • A reverted counterparty looks like a working one. The "proof" it was given never actually succeeded on-chain.
  • A six-figure transfer looks like a handful of ETH. Without a live price, the dollar exposure is invisible.
  • A drained protocol looks like a healthy one. TVL that collapsed an hour ago is not in the prompt.
  • Once signed, there is no undo. A wrong signature is final in a way a wrong sentence never is.

Shield puts a checkpoint between decided and signed: four independent, paid, verifiable answers from a live oracle network, folded into one verdict the agent can act on.

How it works

Four steps from "about to sign" to "here is the evidence".

The same flow runs whether you use the dashboard or call the API. Nothing is pre-computed; every report is built from fresh miner answers at the moment you ask.

  1. Describe the transaction

    Chain (base, ethereum or base-sepolia), recipient address, value in ETH. Optionally a transaction hash to verify a mined transaction, and a protocol name to check liquidity.

  2. Shield queries live miners

    One paid query per applicable check: GAS_PRICE, ONCHAIN_TX_LOOKUP, CRYPTO_PRICE, TVL_LOOKUP. Each is a real x402 payment of $0.01 in USDC, settled on-chain. Shield launches every applicable query at once; the payments themselves are serialized per payer wallet.

  3. Each answer is judged

    Miners answer in plain text. Shield parses the number or status it needs and grades the check pass, warn, fail or error against fixed, public thresholds — with the reason stated.

  4. You get a verdict with receipts

    SAFE, CAUTION or BLOCK, a score out of 100, the reasons, and one card per check showing the miner, its answer, latency, cost and a signal hash the Telegraph node will confirm.

The four checks

What each check asks, who answers, and exactly what the grades mean.

Each check maps one Telegraph intent to explicit, published thresholds. Miners answer in natural-language text (that is what Telegraph validators score), so every parser is defensive: an unparseable answer degrades to warn with a stated reason, never a crash. The thresholds below are exported constants in verdict.ts, so tests and this page stay in sync.

Only the checks your request can use actually run — and only those are paid for. FEE runs on every request; the other three switch on when you supply a transaction hash, a value, or a protocol name.

Verdict rules

Deterministic scoring. Same evidence, same verdict, every time.

There is no model in the loop deciding what "safe" means and no weights to tune. The report starts at 100, each check's grade subtracts a fixed number of points, the total maps to a verdict, and three hard rules that no score can override are applied last.

Points per check grade (start at 100)
GradePointsMeaning
pass0the evidence supports signing
warn−15something needs a second look
fail−35hard evidence against signing
error−10the miner query failed; missing evidence is never free
Score to verdict
ScoreVerdictSuggested action
80 – 100SAFEproceed
50 – 79CAUTIONescalate to a human or a stricter policy
0 – 49BLOCKdo not sign
  • Any fail caps the verdict at CAUTION, even if the score is still 80 or more.
  • Two fails always mean BLOCK, whatever the score.
  • A report where every check errored can never be SAFE. Zero live evidence never green-lights a signature.
  • Verdicts are advisory. Shield never holds the agent's keys and never signs its transactions; the final decision stays with the agent.

The whole algorithm — finalizeReport in verdict.ts

PENALTY = { pass: 0, warn: 15, fail: 35, error: 10 }

score = 100
for check in checks:
  score -= PENALTY[check.status]
score = clamp(score, 0, 100)

verdict = score >= 80 ? SAFE
        : score >= 50 ? CAUTION
        : BLOCK

// hard rules, applied after the threshold
if fails >= 1 and verdict == SAFE: verdict = CAUTION
if fails >= 2:                    verdict = BLOCK
if every check errored and verdict == SAFE:
                                   verdict = CAUTION
// nothing collected at all
if checks is empty: verdict = CAUTION, score = 50

reasons = ["NAME: summary" for each non-pass check]
       or ["All checks passed against live Telegraph
            miner signals."]

Architecture · built on Telegraph

One request in, one paid query per check out, one hash back per answer.

Telegraph Protocol is a decentralized network in which independent miners answer typed questions — intents such as GAS_PRICE, ONCHAIN_TX_LOOKUP, CRYPTO_PRICE and TVL_LOOKUP — over plain HTTP, with validators scoring every answer against ground truth and clients paying per query through x402.

Shield is a consumer of that network: a thin, stateless API in front of it that runs no oracle of its own, never caches answers, never substitutes its own data, and never green-lights a signature without live evidence. Every box below is a real service you can hit yourself.

  • paid request path (x402)
  • answer, signal hash and verification
  • USDC settlement on Base Sepolia

Routing is deterministic

Candidates per intent come from the node's catalog (GET /api/miners, 60 s cache): Truvian 8453 first for its two intents, then curated known-good miners, then the rest by leaderboard rank. First attempt plus one retry to a different miner, 10 s timeout each.

Verdicts are pure functions

buildCheckReport(request, signals) does no I/O and reads no clock. Identical inputs always yield an identical report — the same discipline as the Truvian miner, where determinism is the product.

Failure is evidence, not silence

A miner that times out or rejects payment becomes an error row with the reason attached. The transport module never throws; the verdict engine renders every outcome.

Payment flow: every check is a real x402 v2 payment, settled on-chain.

Shield implements the exact EVM scheme directly from the x402 v2 specification with viem — no @x402/* dependency. The wire format was verified against the live node's 402 challenge before a single USDC moved. Per query: $0.01 (the miner's on-chain minPriceUsdc floor), paid in USDC on Base Sepolia.

  1. server → client

    HTTP 402 challenge

    Shield calls POST /engine/v1/ask/{minerId} with {method, endpoint, payload}. Unpaid, the node answers 402 with a base64 PAYMENT-REQUIRED header. The header is authoritative; the JSON body is only a human summary.

    {
  "x402Version": 2,
  "accepts": [{
    "scheme": "exact",
    "network": "eip155:84532",
    "amount": "10000",                              // atomic USDC = $0.01
    "asset": "0x036CbD53842c5426634e7929541eC2318f3dCF7e", // Circle USDC, Base Sepolia
    "payTo": "0x5a2324aA18613FAD4e44bDF0d6c73Ec1f6D87ff8", // Telegraph Diamond
    "maxTimeoutSeconds": 60,
    "extra": { "name": "USDC", "version": "2" }
  }]
}
  2. client

    Price cap before anything is signed

    The challenged amount is compared with SHIELD_MAX_PAYMENT_USDC (default $0.10). A challenge above the cap is refused and never signed — the payer key cannot be drained by a mispriced miner.

  3. client

    EIP-3009 TransferWithAuthorization, signed offline

    An EIP-712 typed-data signature over the USDC contract's domain, produced with viem. No RPC call, no gas, no allowance transaction — the authorization itself is the payment.

    domain
    { name: "USDC", version: "2", chainId: 84532, verifyingContract: asset }
    primaryType
    TransferWithAuthorization(address from, address to, uint256 value, uint256 validAfter, uint256 validBefore, bytes32 nonce)
    message
    from = payer · to = payTo · value = 10000 · validAfter = now − 600 · validBefore = now + maxTimeoutSeconds · nonce = 32 random bytes
  4. client → server

    Retry with PAYMENT-SIGNATURE

    The same request is re-sent with one extra header: base64 of {x402Version, resource, accepted, payload: {signature, authorization}}, where resource and accepted are echoed verbatim from the challenge. A fresh nonce is generated per attempt; one retry if the facilitator rejects the first.

  5. server → chain

    Verification and gasless settlement

    The node verifies the signature server-side and hands it to the facilitator, which broadcasts transferWithAuthorization on Base Sepolia and pays the gas. The payer wallet holds USDC only — no ETH. The 200 response carries the miner's answer plus a PAYMENT-RESPONSE header with the settlement: {success, transaction, network, payer}. A rejected payment comes back as 402 again with an errorReason (for example invalid_exact_evm_insufficient_balance), which Shield surfaces verbatim on the check card.

  6. client

    Serialized per payer

    The facilitator rejects overlapping authorizations from one payer, so Shield queues payments per process. A four-check report is four sequential paid round-trips — about 10 s end to end, ~2–4 s per check — and nothing is lost to a rejected batch. Cost, latency, miner, transport and signal hash are recorded on every check.

Why you can trust a report

Don't trust the card. Resolve the hash.

A safety tool is only as good as the provenance of its evidence. Every paid answer is recorded by the Telegraph node and identified by a signal_hash. Shield prints it on the check card and in the JSON, and the node exposes a public resolver — so a judge, an auditor or the counterparty can confirm that the evidence Shield shows was really served by that miner, to that wallet, at that time. You are checking the network's record, not Shield's rendering.

Live miners only

Every number on a report was produced by a Telegraph miner at the moment you asked. There is no cache of canned answers, no simulated fallback, no fixture. If a miner is down, the check says so and the score is penalized — Shield will fail a check honestly before it fakes a pass. (The hackathon disqualifies mocked or simulated data; Shield contains none.)

Every query is paid and settled

Each check is a real x402 payment: the node returns HTTP 402, Shield signs an EIP-3009 TransferWithAuthorization with viem, retries with a PAYMENT-SIGNATURE header, and a facilitator settles $0.01 USDC on Base Sepolia on-chain, gaslessly. The cost appears on every card.

Signal hashes anyone can resolve

Resolve any card's hash at https://devnode.telegraphprotocol.com/engine/v1/signal/<hash> and the node returns the recorded signal — miner, wallet, result id and timestamp. No account, no API key.

Open source, with a track record

Shield, the miner behind it and the scoring module are all public at github.com/mrnetwork0001/Truvian. The Truvian miner ranks in ONCHAIN_TX_LOOKUP and GAS_PRICE on the live leaderboard, and Truvian's WASM scoring module held the ONCHAIN_TX_LOOKUP championship twice (registrations 544 and 617).

Verify a check in four steps

  1. Run a check

    In the app or with curl. Each check card shows miner name, latency, cost, transport and a verify signal link.

  2. Copy the signalHash

    From the card link or the checks[i].signalHash field in the JSON.

  3. Resolve it on the node

    GET https://devnode.telegraphprotocol.com/engine/v1/signal/<hash> returns the recorded signal: miner, wallet, result id, timestamp.

  4. Compare

    Miner id and name should match the card; the wallet is Shield's payer; the timestamp brackets the request. The settlement transaction from PAYMENT-RESPONSE is separately visible on Base Sepolia.

Gate the signature

// inside your agent's signing step
const report = await fetch('https://truvian.xyz/api/check', {
  method: 'POST', headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ chain, to, valueEth, txHash, protocol }),
}).then(r => r.json());

if (report.verdict === 'BLOCK')   throw new Error(report.reasons.join('; '));
if (report.verdict === 'CAUTION') await escalate(report);   // human or stricter policy
await sign(tx);                                                // SAFE

FAQ

Questions a founder or a judge would ask.

What does a check cost?

Each check is one paid query to a Telegraph miner at $0.01, settled in USDC on Base Sepolia through x402. A full four-check report is four cents; the three-check example above cost three. Shield pays the miners from its own USDC wallet, and every card shows exactly what was paid.

Which chains are supported?

base (mainnet), ethereum and base-sepolia. Whatever chain you check, the miner payments themselves settle on Base Sepolia — that is where the live Telegraph deployment runs during Season I.

Is a SAFE verdict a guarantee?

No. Verdicts are advisory. Shield surfaces evidence a signing agent would otherwise not have; it does not custody the agent's keys, sign, or block anything itself. Treat BLOCK as a hard stop, CAUTION as "escalate", and SAFE as "the live evidence found nothing wrong" — not as a promise about the counterparty's intentions.

Is any of the data mocked, cached or simulated?

No. Every answer comes from a live Telegraph miner at request time, paid for and stamped with a signal hash. If a miner is unreachable, the check is graded error (or warn for an unavailable TVL) with the reason stated, and the score drops. Shield never fills a gap with a plausible number.

How do I use it from an agent?

Make one POST /api/check before signing and branch on verdict — the snippet in For agents is the whole integration. For a transaction that has already been mined, GET /api/verify/:txHash returns a one-check verification report.

How long does a check take?

About 2–4 seconds per paid check — the 402 challenge, the signed authorization, the retry and the settlement are real network round-trips — and about 10 seconds for a full four-check report. Shield launches every applicable query at once, but the x402 payments are serialized per payer wallet, so the paid round-trips complete one after another.

Why do some reports show fewer than four checks?

Only the checks your input makes possible actually run. FEE always runs; COUNTERPARTY needs a transaction hash; VALUE needs an ETH value; LIQUIDITY needs a protocol name. A check that did not run is not charged and does not affect the score.

Who operates the miners?

FEE and COUNTERPARTY are answered first by Truvian's own miner (id 8453, truvian-onchain-truth). VALUE and LIQUIDITY come from independent live miners on the network such as ChainSight and FinWire. The miner's name is printed on every card, and the explorer lists them all.
